# Agentic Knowledge Gateway を GitHub Copilot で構築するプロンプト

Foundry Toolkit が生成した公式サンプルを出発点に、GitHub Copilot Agent mode で
Agentic Knowledge Gateway を組み上げるためのプロンプト集です。

チュートリアル本文は [`README.md`](README.md) にあります。この文書は、その
「2. Extend the Sample with GitHub Copilot」で使うプロンプトを、判断の根拠と
あわせて詳しくまとめたものです。

> [!NOTE]
> Foundry Agent Service の Memory と incoming A2A はプレビュー機能です。
> ここに書かれた API の形や UI のラベルは変わる可能性があります。

## 1. なぜ 3 段階に分けるのか

一度にすべてを依頼すると、破綻した箇所を特定できません。段階ごとに検証してから
次へ進むことで、問題の切り分けが可能になります。

| 段階 | 目的 | この段階の検証 |
|---|---|---|
| 1 | 不変条件を文書化する | 提案されたファイルを読む |
| 2 | テスト可能な構造へ分割する | `unittest` が通る |
| 3 | 検証と運用のスクリプトを足す | 実際にクラウドで動く |

段階 1 の成果物はコードではなく **プロジェクト指示** です。Copilot は長い会話で
最初の制約を忘れるため、ファイルとして残しておくと後続の指示が安定します。

## 2. プロンプトの書き方

このプロンプト集は次の方針で書かれています。

| 方針 | 理由 |
|---|---|
| 変更してよい範囲を列挙する | 意図しないファイルへの波及を防ぐ |
| **変更してはいけない箇所を明示する** | プロトコル、認証、ポートを守る |
| 「なぜそうするか」を書かせる | 理由がないと一見合理的な別解に置き換えられる |
| 編集前に計画を出させる | 適用前にレビューできる |

特に 3 番目が重要です。たとえば「意味抽出をスキップする」とだけ指示すると、
Copilot は別の実装に変えてしまうことがあります。「意味抽出は非同期で走り、
直接書き込んだ項目を後から書き換えるため」と理由を書かせると、意図が保持されます。

## 3. Prompt 1: ガードレールを確立する

```text
このワークスペースは、Foundry Agent Service の Memory 機能を使う公式の
Agent Framework Responses サンプルです。

編集の前に azure.yaml、main.py、requirements.txt、AGENTS.md を確認してください。
そのうえで、次の不変条件をプロジェクト指示として文書化してください。

アーキテクチャ:
- ResponsesHostServer と Responses 2.0 を維持する
- main.py は dotenv 読み込み、設定、asyncio.run だけを担う薄い入口にする
- FoundryChatClient と Memory プロバイダは同一の AIProjectClient を共有する

設定:
- FOUNDRY_PROJECT_ENDPOINT、AZURE_AI_MODEL_DEPLOYMENT_NAME、
  MEMORY_STORE_NAME、MEMORY_SCOPE を必須にする
- 空値と未解決の ${VAR} や {{VAR}} を拒否する
- load_dotenv(override=False) を使う

認証:
- DefaultAzureCredential を使い、キーやシークレットを追加しない
- .env、トークン、資格情報をコミットしない

境界の明示:
- MEMORY_SCOPE は固定の共有スコープであり、利用者ごとの分離ではない
- 合成の非機微データだけを扱う
- Memory と A2A はプレビュー機能として記述する

失敗の扱い:
- Memory へアクセスできない場合は起動時に明確に失敗させる
- 広い except で捕捉して静かに機能低下させない

作業範囲:
- クラウドリソースの作成や削除は行わない
- 焦点を絞った unittest を追加する

編集する前に、追加または変更するファイルの一覧を示してください。
```

### この段階で確認すること

- 生成された指示ファイルに、上記の項目が漏れなく反映されているか
- `MEMORY_SCOPE` が利用者ごとの分離として書かれていないか
- コードがまだ変更されていないか

## 4. Prompt 2: テスト可能なモジュールへ分割する

```text
Hosted Agent の契約を変えずに、生成されたサンプルをリファクタしてください。

モジュール分割:
- gateway/settings.py: 型付きの環境変数検証
- gateway/memory_config.py: 7日間の Memory Store 定義とドリフト検出
- gateway/memory_proof.py: 不透明なキーと値の検証と生成
- gateway/memory_tools.py: 明示的な書き込みツール
- gateway/memory_provider.py: 意味検索の振る舞い調整
- gateway/app.py: 上記を組み立てて ResponsesHostServer を起動

Memory Store の定義:
- user_profile を有効にし、chat_summary と procedural_memory を無効にする
- 既定 TTL を 604800 秒にする
- 資格情報や機微データを保存しない旨を store の指示に含める

厳密な書き込みツール:
- akg で始まる 16 桁の 16 進数のキーと、akv で始まる 16 桁の 16 進数の値だけを
  受理する
- Memory の項目作成 API で 1 件の user-profile 項目として逐語で書き込む
- サービスが返した内容が要求と一致しない場合は失敗させる

意味抽出との競合回避:
- FoundryMemoryProvider を継承し、厳密なペアを含むターンでは after_run の
  意味更新をスキップする
- 理由をコメントで説明する。意味抽出は非同期で走り、直接書き込んだ項目を
  後から書き換える可能性があるため

クライアント設定:
- allow_preview=True、update_delay=0、store=False を設定する

起動時の検証:
- サーバー起動前に、埋め込みを伴う実際の Memory 検索を 1 回実行する
- Store 作成は成功しても埋め込みモデルへの権限が未反映の状態を検出するため

テスト:
- 設定、Memory 定義、証明形式、書き込みツールの unittest を追加する

Memory を無効化する広い例外処理は追加しないでください。
```

### なぜ書き込み経路が 2 つ必要か

Memory は会話から情報を抽出するとき、内容を **要約したり一般化したり** します。
公式ドキュメントも、統合処理で LLM が重複や矛盾を解決すると説明しています。

通常の記憶としては妥当ですが、検証用の値には使えません。`akg...=akv...` のような
値は 1 文字でも変われば証拠になりません。

| 経路 | 保存内容 | 用途 |
|---|---|---|
| 意味抽出（自動） | 要約・一般化された内容 | 通常の好みや事実 |
| 明示的な書き込みツール | 逐語 | 検証用の不透明なペア |

さらに意味抽出は非同期で走ります。ペアを書いた直後に同じ項目を書き換える競合が
起きるため、ペアを含むターンでは `after_run` 自体をスキップします。

### この段階で確認すること

- `unittest` が通るか
- `after_run` をスキップする理由がコメントに書かれているか
- 起動時の Memory 検索が実装されているか

## 5. Prompt 3: 検証と運用のスクリプトを追加する

```text
Hosted ランタイムの依存関係とは分離した開発者向けスクリプトを追加してください。

プロビジョニング:
- provision_memory_store.py: 冪等な作成、読み戻し、7日 TTL、ドリフト検出、
  埋め込みを伴うアクセス確認
- 非互換な設定を検出したら停止する。自動で削除や再作成をしない

証明:
- memory_proof.py: 実行ごとに独立した不透明なキーと値を生成する
- memory_polling.py: 既知の一時障害だけを期限内でリトライする
- verify_memory.py: 1 件の項目に現在のペアが完全一致することを要求し、
  書き込み前の不在確認にも対応する

管理:
- cleanup_memory.py: 明示的な確認の後にのみスコープまたは Store を削除する
- list_memory.py: 現在のスコープの内容を一覧表示する

A2A:
- configure_a2a.py: Responses を維持したまま incoming A2A を追加する。
  protocol_configuration と Agent Card version 1.0 を使い、served card を検証する
- a2a_client.py: DefaultAzureCredential で認証し、agentCard/v1.0 を取得し、
  JSONRPC の v1.0 supportedInterface を要求し、非ストリーミングで送信する

A2A クライアントの判定基準:
- エージェントの応答文は診断シグナルとして扱い、判定には使わない
- 権威ある Memory API の返却値で永続性を判定する
- 応答がペアを復唱しなかった場合は待機時間を短縮し、それでも見つからなければ
  ツール呼び出しが完了しなかったと報告する
- 新しいタスクからキーだけで問い合わせ、独立生成した値が返ることを確認する

メタデータ:
- sync_agent_metadata.py: 解決済みの azd 値から環境固有のメタデータを生成し、
  アカウントのエンドポイントをコミットしない

依存関係:
- a2a-sdk とテスト専用パッケージは requirements-dev.txt に入れる
- Hosted ランタイムの requirements.txt には含めない

その他:
- VS Code タスクと、焦点を絞った unittest を追加する

古い protocols 配列を使わないでください。また、served A2A v1.0 Agent Card の
protocolVersion がトップレベルにあると仮定しないでください。
supportedInterfaces の中にあります。
```

### なぜ応答文を判定に使わないか

初期の実装は、エージェントがペアを復唱しないと検証を開始しませんでした。モデルの
言い回しは実行ごとに変わるため、書き込みが成功していても検証が止まります。

チュートリアルの原則は「エージェントの発話は永続性の証拠ではない」です。判定は
権威ある Memory API の返却値だけで行います。応答文は待機時間を調整するための
参考情報にとどめます。

### この段階で確認すること

- ローカルで Responses が動くか
- 証明の手順が通るか（不在確認、書き込み、直接検証、新セッションでの想起）
- A2A クライアントが応答文の有無に関わらず判定できるか

## 6. レビューチェックリスト

次の差分は拒否してください。

| # | 拒否する変更 | 理由 |
|---|---|---|
| 1 | API キー、トークン、実値入り `.env` の追加 | 認証方式の破壊 |
| 2 | `DefaultAzureCredential` の置き換え | 同上 |
| 3 | 固定スコープを利用者分離と記述 | 事実と異なる |
| 4 | 起動後に Memory を任意扱いにする | 静かな機能低下 |
| 5 | A2A 追加時に Responses を削除 | 既存契約の破壊 |
| 6 | A2A v0.3 のみを想定したカード検証 | 現行仕様と不一致 |
| 7 | モデルの応答文を永続性の証拠とする | 検証にならない |
| 8 | 意味抽出に逐語保存を期待する | LLM が統合・要約する |
| 9 | 想起クエリに期待値を含める | 質問文から読み取れる |
| 10 | 環境固有メタデータのコミット | 環境削除後に壊れた設定が残る |
| 11 | 非互換な Store の自動削除・再作成 | データ喪失 |
| 12 | A2A 開発依存を Hosted 側に混入 | デプロイ肥大化 |

7 から 9 が最も重要です。これらを見逃すと、動いているように見えて実際には
検証できていないシステムになります。

## 7. 想定と異なる提案が出たとき

Copilot は同じプロンプトでも毎回同じコードを生成しません。次のように差し戻せます。

```text
azure.yaml は変更対象外です。その変更を取り消して、指示した項目だけに絞って
ください。
```

```text
変更するファイルと、それぞれの変更理由を一覧で示してください。
```

```text
after_run をスキップする理由をコメントに残してください。意味抽出が非同期で
走り、直接書き込んだ項目を上書きし得るためです。
```
